# 数据保护与验收

## 建模选择

已有单 JSON 账本可继续使用 `categoryBudgets`、`items`、`toBuyItems`、`planItems`；新建也可采用逐条关系表。重点是稳定编号、权限边界、事务和冲突检测，而非强制某种表结构。

采用单 JSON 结构时，至少有账本 ID、content、revision、服务器更新时间和受保护的历史表。多用户使用 owner/user 标识隔离账本，不能只靠一个可猜测的账本 ID 区分权限。

## 保存与同步

1. 本机保存待上传修改，同时保留最近一次确认的云端基准版本。浏览器存储失败要明确提示并保留内存导出机会，不谎称已保存。
2. 服务端在同一事务中校验用户权限、结构、金额及稳定编号；锁定或条件更新当前版本。预期版本不符则返回冲突，不写入数据。
3. 保存前后的历史与新版本更新必须原子完成。限制客户端绕过版本接口直接写表；仅在前端判断版本不足以防止旧页面覆盖。
4. 合并应比较基准、本机、远端三份数据。不同编号的独立修改可合并；同一条目的冲突、删除与修改冲突，以及采购归档与关联支出必须整体核对。
5. 远端应用到界面时不能被深度监听当成新的用户修改再次上传。读取错误不能被当成空表，更不能据此上传默认示例数据。
6. 上传超时不等于没有保存。重试先读取版本并核对内容，使用稳定编号或幂等键防止重复入账。
7. 联网、回到页面及适度轮询时重试或检查。若启用 Realtime，须实测订阅生效，不能把连接成功等同于数据事件可用。

同步状态区别等待上传、正在上传、已同步、读取失败、上传未确认和版本冲突。成功提示只在服务端确认后出现。显示服务器真实保存时间；仅轮询而没有修改时，不应更新时间制造“刚保存”的假象。

## 备份与恢复

- 保存云端历史版本；如有运维条件，再配置独立备份，说明保留策略。
- 本机近期快照可默认保留 40 份，并提供完整 JSON 导出和导入预览。浏览器副本会受清理网站数据影响，不能作为唯一备份。
- JSON 导出涵盖预算、支出、待购、进度、关联关系及恢复所需元数据。CSV 可供阅读，但不是完整恢复格式。
- 恢复前先备份当前状态，展示新增、修改、删除和关联冲突；默认补回缺少编号，不静默覆盖同编号记录或目标预算。
- 识别“计划已完成但支出缺失”“原计划仍待购但导入已完成档案”等组合，避免恢复后重复计费。
- 已遗失数据只能依赖实际存在的历史、备份或设备缓存恢复。新建历史功能不能恢复此前已被覆盖的数据，不根据用户口述伪造原记录。

## 针对修改选择测试

使用独立测试库或模拟响应，不向真实账本提交测试支出。仅在改动涉及该功能时运行下列相应场景，并保留必要回归测试：

| 场景 | 应验收结果 |
|---|---|
| 修改子预算、实付或备注 | 六大目标预算不被联动修改；总预算仍只求六项和 |
| 计划预算 5000，实际支付 4800 | 预测中用 4800 替换 5000；只生成一条支出 |
| 分类和日期筛选 | 仅改变计划列表，整体预测不变 |
| 两设备各新增一条 | 最终两条都保留 |
| 两设备修改同一条、删除与修改竞争 | 暂停自动覆盖并保留冲突版本 |
| 断网新增、刷新再联网 | 本机新增仍存在，确认后补传 |
| 读取失败、主记录缺失、损坏缓存、存储满 | 不上传默认账本，不显示虚假成功 |
| 旧页面直接写入、错误版本提交 | 数据库拒绝，现有账本不变 |
| 上传成功但响应丢失、上传中再次编辑 | 重试不重复，后续编辑不丢失 |
| 完成采购、重复点击或两端同时完成 | 计划和实际支出关系一致，不重复计费 |
| 多图部分失败与重试、长图重叠 | 保留成功结果、不重复统计重叠交易 |
| 新计划识图、已有计划识图 | 确认前不写；确认后新增一次或更新原编号 |
| AI 未知金额、日期、缺失字段 | 不猜金额，不误用付款日期，不清空原值 |
| AI 返回受保护字段、多个候选 | 不修改编号或关联支出，由用户选候选 |
| 关闭识图、取消请求、切换计划后收到响应 | 不污染新表单或旧记录 |
| 编辑弹窗打开后远端修改同项 | 旧表单提交被拦截，要求重新核对 |
| 历史保存或恢复 | 版本更新与留档一致，恢复不覆盖之后的新改动 |
| 私人账本权限 | 未登录和其他用户均不能读写；仅本人可操作 |

还应检查手机端新增、编辑、确认、取消、底部导航及软键盘后的实际可用性。报告自动测试、模拟接口、真实模型调用、生产验证各自的范围，不混为一谈。
